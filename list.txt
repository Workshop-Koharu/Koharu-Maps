# 프로젝트 마스터 개발 명세서 — Koharu Maps

## Zero-Dependency Standalone GIS \& Offline Cartographic Engine

---

# 0\. 프로젝트 선언

당신은 세계 최고 수준의 GIS(Geographic Information System), Cartographic Engineering, Computational Geometry, Computer Graphics, Spatial Database, Navigation Algorithm 분야의 전문 소프트웨어 아키텍트이자 시니어 시스템 엔지니어다.

이번 프로젝트의 목적은 기존 지도 서비스에 의존하지 않는 완전 독립형 지도 소프트웨어 **Koharu Maps**를 개발하는 것이다.

단순히 지도 API를 대체하거나 기존 지도 SDK를 감싸는 웹 애플리케이션을 만드는 것이 아니다.

지도 데이터의 내부 표현, 공간 데이터베이스, 좌표 변환, 지도 투영, 벡터 렌더링, 지형 렌더링, 공간 인덱싱, 지리정보 검색, 경로 탐색, 지도 타일 생성, 오프라인 데이터 관리에 이르기까지 핵심 시스템을 직접 설계하고 구현한다.

최종 결과물은 인터넷 연결이 완전히 차단된 환경에서도 정상적으로 작동하는 독립형 지도 시스템이어야 한다.

20. 실제 구현하지 않은 기능을 구현 완료로 표시하는 행위 금지.

OpenStreetMap, 공개 지리정보 데이터, 공공기관의 지리정보 등은 별도의 라이선스 및 사용 조건을 검토한 후 데이터 원본으로 활용할 수 있다. 단, 외부 지도 서비스를 호출하거나 타사 지도 렌더링 엔진을 사용하는 것은 허용하지 않는다.

지도 엔진 자체는 독립적으로 구현한다.

외부 데이터의 사용 여부와 관계없이 데이터 파싱, 내부 자료구조 변환, 공간 인덱싱, 렌더링, 경로 탐색은 자체 구현을 원칙으로 한다.

# 4\. Coordinate Reference System

좌표계 처리 시스템을 독립적으로 구현한다.

## 4.1 기본 좌표계

지원할 좌표계:

- WGS84
- EPSG:4326
- Web Mercator
- EPSG:3857
- 대한민국에서 사용되는 주요 투영 좌표계

## 4.2 좌표 변환 엔진

다음 변환을 구현한다.

1. Geographic Coordinate → Projected Coordinate
2. Projected Coordinate → Geographic Coordinate
3. Geographic Coordinate → Screen Coordinate
4. Screen Coordinate → Geographic Coordinate
5. World Coordinate → Local Coordinate
6. Local Coordinate → World Coordinate

## 4.3 지도 투영

초기 구현은 Web Mercator를 기본 투영으로 사용한다.

추가적으로 대한민국의 지리적 특성을 고려한 TM 계열 투영법을 지원할 수 있도록 구조를 설계한다.

## 4.4 정밀도

- Double Precision 기반 좌표 연산
- Floating Point Error 관리
- Coordinate Normalization
- Longitude Wrapping
- Latitude Boundary Validation
- Projection Singularities 처리

좌표 변환 과정에서 발생하는 오차를 테스트한다.

# 7\. Map Tile Engine

독립적인 타일 관리 및 생성 시스템을 구현한다.

## 7.1 타일 구조

타일은 Zoom Level, X Coordinate, Y Coordinate를 기반으로 관리한다.

타일 인덱싱 공식은 사용하는 투영 체계에 맞춰 직접 구현한다.

## 7.2 타일 기능

- Tile Generation
- Tile Loading
- Tile Caching
- Tile Eviction
- Tile Prefetching
- Tile Boundary Calculation
- Tile Dependency Management

## 7.3 타일 저장 포맷

자체 바이너리 컨테이너를 설계한다.

권장 구조:

KMAP
│
├── Header
├── Version
├── Coordinate Reference
├── Geographic Bounds
├── Zoom Metadata
├── Layer Metadata
├── Tile Index
├── Tile Payload
└── Integrity Checksum

데이터 손상 여부를 확인할 수 있어야 한다.

향후 포맷 버전이 변경되어도 이전 데이터의 마이그레이션이 가능해야 한다.

# 8\. Geographic Data Engine

지도 데이터의 수집 이후 처리 과정을 전담하는 시스템이다.

## 8.1 데이터 가져오기

지원할 수 있는 원본 형식:

- GeoJSON
- Shapefile
- CSV 좌표 데이터
- 자체 바이너리 포맷
- 일반적인 지리정보 데이터 형식

단, 외부 GIS 엔진을 통해 데이터를 렌더링하거나 처리하는 방식은 사용하지 않는다.

각 형식의 파서는 직접 구현한다.

## 8.2 데이터 정규화

원본 데이터를 내부 표준 모델로 변환한다.

처리 항목:

- 좌표계 정규화
- Geometry Validation
- 중복 객체 제거
- 속성 정규화
- ID 정규화
- Bounding Box 생성
- 공간 인덱스 생성
- 데이터 무결성 검사

## 8.3 데이터 계층

데이터를 다음과 같이 분리한다.

1. Terrain Layer
2. Water Layer
3. Road Layer
4. Building Layer
5. Boundary Layer
6. Railway Layer
7. Place Layer
8. Label Layer

각 계층은 독립적으로 활성화 및 비활성화할 수 있어야 한다.

- 두 Geometry의 교차 여부
- 가장 가까운 객체 검색
- 특정 도로에 연결된 객체 검색

- Query Cache
- Incremental Search

대규모 데이터에서도 검색 응답 시간이 안정적으로 유지되도록 한다.

# 10\. Navigation Engine

자체 내비게이션 엔진을 구현한다.

외부 경로 탐색 API는 절대로 사용하지 않는다.

## 10.1 Road Graph

도로를 그래프로 표현한다.

Graph:

- Vertex
- Edge
- Edge Weight
- Direction
- Road Type
- Access Restriction
- Speed Metadata
- Turn Restriction

도로의 실제 연결 관계를 유지해야 한다.

단순히 도로의 양 끝점을 연결하는 방식으로 구현해서는 안 된다.

## 10.2 경로 탐색 알고리즘

초기 구현:

- Dijkstra Algorithm
- A\* Search

추가적으로 다음을 검토한다.

- Bidirectional Search
- Contraction Hierarchies
- ALT Algorithm
- Hierarchical Routing

## 10.3 경로 계산 기준

- 최단 거리
- 예상 이동 시간
- 도로 유형
- 도로 연결 관계
- 일방통행
- 접근 제한
- 회전 제한

## 10.4 경로 표현

경로 결과는 다음 정보를 포함한다.

- 출발 좌표
- 도착 좌표
- 전체 거리
- 경로 Geometry
- 경유 지점
- 예상 이동 시간
- 구간별 도로 정보
- 회전 안내 정보

## 10.5 내비게이션 안내

자체 경로 분석 결과를 이용해 다음과 같은 안내 문장을 생성한다.

- 직진
- 좌회전
- 우회전
- 유턴
- 도로 진입
- 교차로 통과
- 목적지 도착

실제 교통 상황이나 실시간 교통량을 인터넷 없이 자동으로 확보할 수 있다고 가정하지 않는다.

# 11\. Geocoding Engine

주소와 좌표 사이의 변환 시스템을 구현한다.

## 11.1 Forward Geocoding

주소 문자열을 분석하여 좌표를 반환한다.

예시:

대한민국
→ 충청남도
→ 천안시
→ 서북구
→ 성정동
→ 도로명 및 건물 번호

## 11.2 Reverse Geocoding

위도와 경도를 입력받아 해당 위치에 대응하는 주소 및 행정구역 정보를 반환한다.

## 11.3 주소 데이터 모델

- Country
- Province
- City
- District
- Neighborhood
- Road Name
- Building Number
- Postal Code
- Coordinate

주소 검색은 사전에 구축된 로컬 데이터베이스만 사용한다.

# 12\. Offline-First Architecture

이 프로젝트의 필수 조건이다.

애플리케이션은 네트워크 연결이 없어도 모든 핵심 기능을 사용할 수 있어야 한다.

## 12.1 오프라인 실행

다음 조건을 만족해야 한다.

- 최초 실행 시 인터넷 연결 불필요
- 지도 데이터 로컬 로딩
- 지도 렌더링 로컬 처리
- 장소 검색 로컬 처리
- 주소 검색 로컬 처리
- 경로 탐색 로컬 처리
- 사용자 설정 로컬 저장
- 즐겨찾기 로컬 저장
- GPS 사용 시 인터넷 불필요

GPS 수신은 위성 신호를 이용하며, GPS 하드웨어와 운영체제 지원이 필요하다.

## 12.2 네트워크 독립성

프로그램의 정상적인 실행 과정에서 외부 네트워크 요청이 발생해서는 안 된다.

다음 항목을 검증한다.

- DNS 요청
- HTTP 요청
- HTTPS 요청
- 외부 WebSocket
- 원격 이미지 요청
- CDN 리소스 요청
- 외부 폰트 요청
- 원격 지도 타일 요청

인터넷이 차단된 환경에서 전체 기능을 테스트한다.

## 12.3 로컬 데이터 관리

사용자는 로컬 지도 데이터의 설치, 삭제, 백업, 복원 및 무결성 검사를 할 수 있어야 한다.

# 13\. Terrain Engine

## 13.1 지형 표현

- Elevation Data
- Digital Elevation Model
- Contour Line
- Hillshade
- Slope
- Terrain Shading
- Terrain Mesh

## 13.2 지형 렌더링

높이 데이터를 기반으로 지형 메시를 생성하고 GPU에 전달한다.

추가적으로 다음 기능을 지원할 수 있도록 설계한다.

- 2D Terrain
- 2.5D Terrain
- 3D Terrain
- Elevation Visualization

지형 데이터가 없는 지역은 임의의 실제 지형을 만들어내지 않는다.

---

# 14\. Label \& Symbol Engine

지도에 표시되는 지명과 시설물 명칭을 처리한다.

## 14.1 라벨 배치

한글 글꼴의 자소 결합과 글리프 처리에 문제가 없어야 한다.

# 19\. 개발 단계

## Phase 1 — Core Foundation

- 빌드 시스템 구축
- 좌표계 구현

- 기본 Geometry 모델 구현
- 기본 지도 화면 구현

완료 기준: 빈 지도 화면에서 좌표 기반 객체를 정확하게 표시할 수 있어야 한다.

## Phase 2 — Rendering Engine

- GPU 렌더링
- 벡터 도형 렌더링
- 도로 렌더링
- 건물 렌더링
- 지도 레이어
- 확대 및 축소
- 화면 이동

완료 기준: 로컬 벡터 데이터를 실제 지도처럼 렌더링할 수 있어야 한다.

## Phase 3 — Geographic Data

- 데이터 파서
- 데이터 정규화
- 공간 데이터 저장
- 공간 인덱스
- 지도 데이터 검증
- 타일 데이터 생성

완료 기준: 실제 지리정보 데이터를 내부 포맷으로 변환하고 렌더링할 수 있어야 한다.

## Phase 4 — Spatial Search

- 장소 검색
- 주소 검색
- 공간 질의
- 근접 검색
- Reverse Geocoding

완료 기준: 인터넷 없이 로컬 지리정보를 검색할 수 있어야 한다.

## Phase 5 — Navigation

- Road Graph
- A\* 알고리즘
- Dijkstra 알고리즘
- 경로 Geometry 생성
- 거리 계산
- 회전 안내

완료 기준: 실제 도로 연결 데이터를 이용해 출발지에서 목적지까지 경로를 계산할 수 있어야 한다.

## Phase 6 — Offline System

- 로컬 지도 데이터 패키지
- 데이터 관리
- 오프라인 검색
- 오프라인 경로 탐색
- 네트워크 의존성 제거
- 완전 오프라인 테스트

완료 기준: 네트워크 어댑터를 비활성화한 상태에서 모든 핵심 기능이 정상 작동해야 한다.

## Phase 7 — Optimization

- 렌더링 최적화
- 메모리 최적화
- CPU 최적화
- GPU 최적화
- 대용량 데이터 테스트
- 안정성 테스트

완료 기준: 대규모 지도 데이터에서 안정적으로 작동해야 한다.

## Phase 8 — Final Release

- 사용자 인터페이스 완성
- 설정 시스템
- 데이터 관리 시스템

- 배포 패키지

# 21\. 개발 및 코드 작성 규칙

다음 규칙을 반드시 준수한다.

- 실제 작동하는 코드만 작성한다.
- 가짜 기능을 만들지 않는다.
- Placeholder를 사용하지 않는다.
- TODO로 핵심 기능을 미루지 않는다.
- 존재하지 않는 라이브러리 API를 사용하지 않는다.
- 임의의 데이터로 실제 지도처럼 보이게 만드는 행위를 금지한다.
- 구현하지 않은 기능을 완성했다고 보고하지 않는다.
- 예외 처리를 누락하지 않는다.
- 모듈 간 결합도를 최소화한다.
- 명확한 자료형을 사용한다.
- 메모리 및 리소스 수명을 명시적으로 관리한다.
- 알고리즘의 시간 및 공간 복잡도를 고려한다.
- 핵심 알고리즘은 단위 테스트를 작성한다.
- 코드 중복을 최소화한다.
- 기존 프로젝트 구조를 존중한다.
- 기존 기능을 임의로 삭제하지 않는다.
- 빌드 오류를 남겨두지 않는다.

기능 구현이 완료되면 실제 실행 및 테스트 결과를 확인한다.

**Koharu Maps는 기존 지도 서비스를 사용하는 애플리케이션이 아니라 독립적인 지도 엔진을 보유한 GIS 소프트웨어여야 한다.**
